## 一、本项目定位画像

### 1.1 核心定位

**一个零依赖、零构建、可离线运行的小鹤双拼练习网页应用。**

从代码结构反推出的三条设计主线（这三条决定了它与同类项目的根本差异）：

| 主线 | 具体表现 | 代价 |
|---|---|---|
| **零依赖** | 运行时**完全无第三方库**。`src/` 下全部是原生 ES Module；`package.json` 只存在于 `_test/`（测试用 linkedom），不参与应用运行 | 无法用 TS/框架/组件库，`main.js` 已 2295 行 |
| **零构建** | `index.html` 直接 `<script type="module" src="src/main.js">`，改完刷新即生效 | 必须起 HTTP 服务（`file://` 下 ES Module 被 CORS 拦截） |
| **离线优先** | 题库、方案、图表全部内置。`ui/chart.js` 是手写 Canvas 图表，**刻意不引图表库** | 图表能力受限，只有折线/柱状两种 |

> **关键取舍**：为了「零依赖」，本项目付出了 `file://` 不能直接双击的代价（ES Module 的硬限制），
> 只能靠 `启动双拼练习.bat` 起本地服务来补偿。这是一个**用一点使用摩擦换取架构纯净**的选择。

### 1.2 技术栈

```
语言      原生 JavaScript（ES2020+，ES Module）
样式      原生 CSS（单文件，CSS 变量着色）
图形      SVG 手绘键盘（ui/keymap.js）+ Canvas 手绘图表（ui/chart.js）
存储      localStorage（带内存降级 + 配额恢复 + 键维度错误统计）
测试      三套自研零依赖脚本（verify / engine / integration）+ linkedom 驱动集成测试
CI        GitHub Actions（Node 18/20/22 三版本矩阵）
分发      Windows .bat 一键启动（含手写 Shell Link 生成桌面快捷方式）
```

**没有的东西**（要明确）：应用运行时无 TS、无框架、无打包器、无 npm 依赖树、无 Lint 配置。
（`_test/` 下有一个用于集成测试的 `package.json` + 锁文件，属于开发期工具，可整个删除。）

### 1.3 架构分层

```
┌─────────────────────────────────────────────┐
│  main.js (2295行)  应用装配 / 视图渲染 / 事件 │  ← 唯一的大型文件
├─────────────────────────────────────────────┤
│  ui/     keymap.js(SVG键盘+热力图) chart.js  │
├─────────────────────────────────────────────┤
│  core/   engine.js(状态机)   questions.js    │
│          scheme.js(方案)     stats.js(统计)  │
│          storage.js(存储)    tokenizer.js    │
│          score.js(测验评分)                  │
├─────────────────────────────────────────────┤
│  data/   pinyin.js(1107字/299词/45短文)      │
└─────────────────────────────────────────────┘
```

**分层是干净的**：`core/` 完全不碰 DOM，`ui/` 只做渲染、不含业务逻辑，`data/` 是纯数据。
`scheme.js` 把方案抽象成「拆解候选数组」而不是单一答案，这一点设计得比多数同类项目更严谨
（因为 `xian` 可以是 `x+ian` 也可以是 `xi+an`，单一答案会误判）。

### 1.4 功能清单（据代码复核）

| 模块 | 能力 | 状态 |
|---|---|---|
| 练习模式 | **8 种**：键位熟悉 / 只听声母 / 只听韵母 / 声韵拆分 / 单字(7档递进) / 词组 / 短文跟打 / **能力测验** | ✅ |
| 实时反馈 | 逐键校验、错误时给正确键+拆分方式、实时速度/正确率/用时/连击 | ✅ |
| **卡住自动提示** | 停留 3 秒键位图闪该键（只给位置）→ 6 秒给答案；`Tab` 手动求助；节奏可调可关 | ✅ |
| **提示统计口径** | 提示过的字符不计入**独立正确率**分子，与表面正确率分开统计 | ✅ |
| 键位图 | 交互式 SVG，实时高亮声母/韵母/零声母，按对/按错/待按各有状态色 | ✅ |
| **错误热力图** | 26 键着色，范围可切 全部 / 近 30 次 / 近 10 次（P90 归一化） | ✅ |
| 统计 | 每日数据、速度/正确率/字数三种曲线（日/周/月）、易错字词表 | ✅ |
| 复习 | 易错项按「错误次数 × 时间衰减 × 掌握惩罚」加权，一键生成复习题 | ✅ |
| **能力测验** | 无提示无求助的混合卷，完成后按「正确率 70 + 速度 30 + 完成度」给 0–100 分与 S/A/B/C/D/E 等级 | ✅ |
| **新手引导页** | 「为什么用双拼」独立说明页：原理对比表 + 6 条好处 + 3 个诚实代价 + 4 周时间线 | ✅ |
| 体验 | 自定义时长/题量、暂停续练、现场恢复、JSON 导出**导入合并（按 id 去重）** | ✅ |
| 容错 | 存储降级、配额恢复、脏数据过滤、非 2 键音节全量拦截 | ✅ |

### 1.5 工程化亮点（已做得比同类好的部分）

- **测试组织**：三套独立套件（verify 方案正确性 / engine 引擎逻辑 / integration 全应用），
  `verify.mjs` 里有**全量遍历断言**——所有音节逐个校验必须 2 键。
- **确定性回归**：针对易错点写死断言，例如「L1 声母题里 zh/ch/sh 的答案必须是单键」
  「零声母恒为 2 键、顶层 `zero` 字段须与 `split.zero` 一致」——
  这类断言能挡住「看起来对但实际错」的改动。
- **依赖可复现**：集成测试的依赖用 `_test/package.json`（精确版本）+ `package-lock.json` 锁定，
  配 `npm ci` 与 CI 矩阵，「换个环境结果不一样」的问题已被消除。
- **文档**：README 记录了「容易踩的坑」；`_test/README.md` 说明了测试环境的降级垫片
  （明确区分「测试框架缺陷」与「应用缺陷」），这个意识很少见。
- **构建期脚本与运行时严格分离**：`_test/` 可整个删除，不影响应用。

## 二、同类项目逐一分析

> 本章结论经复核**仍然有效**，保留初版内容（仅更新个别与本项目现状相关的表述）。

### 2.1 BlueSky-07/Shuang —「双拼练习」（最经典）

**简介**：最早流行起来的双拼练习工具。有 Web 版与微信小程序版，被纸砚等项目公开致谢为灵感来源。

**值得借鉴的设计**

| 设计 | 内容 | 本项目是否适用 | 优先级 |
|---|---|---|---|
| **多方案支持** | 内置 20+ 方案：自然码/搜狗/微软/小鹤/智能ABC/拼音加加… | ✅ 适用 | **P0（未做）** |
| **方案配置与代码分离** | 新增方案 = 加一份映射配置 + 注册，**不改核心逻辑** | ✅ 适用 | **P0（未做）** |
| **出题模式分层** | 全部随机 / 顺序 / 困难随机 / 无拼音提示 | ✅ 适用 | P1 |
| **键位图自动渲染** | 构建期从配置渲染 SVG/PNG | ⚠️ 本项目运行时渲染，更灵活，不需要 | P3 |
| **多平台适配** | Web + 小程序共用核心 | ⚠️ 小程序需重构 DOM 层，成本高 | P3 |

**最值得学的一点**：它的「新增一个双拼方案」是一条**文档化的 8 步流程**。
本项目目前把方案硬编码在 `scheme.js` 里，**加第二套方案要改核心代码**——这一条仍然成立。

**要规避的坑**：它的键位图渲染对浏览器有依赖，**曾出现过文字重叠问题**。
本项目正好踩过同一个坑（H 键 `ang` 与提示文字重叠），并且**用几何断言测试守住了**。

### 2.2 Yidadaa/shuangpin —「纸砚」

**简介**：Vite + TypeScript + Vitest 构建，支持声母/韵母/长句模式、自定义方案、进度统计、深色模式、成就系统。

**值得借鉴的设计**

| 设计 | 内容 | 本项目是否适用 | 优先级 |
|---|---|---|---|
| **练习模式按「知识点」划分** | 随机 / 声母 / 韵母 / 长句 | ✅ **已完成**（对应本项目 L2a/L2b） | — |
| **自定义方案配置格式** | 一行同时声明 键位/韵母/声母；`zeroMap` 声明零声母 | ✅ 适用 | P1（未做） |
| **本地自定义方案** | 用户可在设置里现场新增方案，不必改源码 | ✅ 适用 | P1 |
| **Vitest + Husky + ESLint + Actions** | 完整工程化链路 | ⚠️ 与「零依赖」冲突（CI 已单独补上） | P2 |
| **多音字处理** | 候选过长时截断显示，但**仍可正常判定** | ⚠️ 本项目短文已覆盖，多音字未专门处理 | P2 |
| **成就系统** | 持续激励 | ✅ 适用，成本低 | P2 |

**最值得学的一点**：「声母模式 / 韵母模式」这个切分方式比整体拆分更对症 ——
**本项目已经实现这一条**（L2a 只听声母 / L2b 只听韵母）。

**要规避的坑**：README 的 FAQ 明确写着「一对多的双拼映射关系**未做兼容**」。
也就是说：**开放自定义方案后，必须定义并校验「方案合法性」**，否则会遇到
「双拼码 → 拼音」一对多导致判定歧义。本项目若要支持多方案，必须一并设计这层校验。

### 2.3 z1803406304/shuangpin-practice —「双拼练习系统」（与本项目定位最接近）

**简介**：小鹤双拼专用。七种模式、卡住自动提示、错误热力图、历史复盘、易错复习，可打包成单文件 HTML。

**这是与本项目最可比的一个**——同样是「小鹤专用 + 离线 + 本地存储」。

**值得借鉴的设计**

| 设计 | 内容 | 本项目状态 | 优先级 |
|---|---|---|---|
| 卡住自动提示 | 干等 3 秒闪键位；提示过的题不计入独立正确率 | ✅ **已实现**（3 秒闪 / 6 秒给答案 / Tab 求助） | — |
| 错误热力图 | 本轮 + 历史多轮累计 | ✅ **已实现**（含范围切换） | — |
| **结算面板三维度** | 「最常按错的键」/「最容易错的字」/**「反应最慢的键」** | ⚠️ **前两项有，第三项没有** | **P1** |
| 数据驱动题库 | 按真实字频加权 | ⚠️ 本项目按常用度分 7 档，**未按字频加权** | P1 |
| 键盘布局无关 | 用 `KeyboardEvent.code`（物理键位）判定 | ❌ **未做**（用的是 `e.key`） | P1 |
| **离线单文件** | 构建期产出单文件 HTML，双击即用 | ❌ **未做** | **P1** |
| 导入导出去重 | 合并按 id 去重 | ✅ **已实现** | — |
| 热力图时间范围切换 | 全部 / 近 30 轮 / 近 10 轮 | ✅ **已实现** | — |
| 提示分级 | 默认闪键位；Tab 看答案；可设 6 秒后显示答案 | ✅ **已实现** | — |
| 暂停时不计时/不计错/不误触发提示 | 准备阶段与离开时全免 | ✅ **已实现**（`integration.mjs`【10b】有断言） | — |

**复核结论**：初版报告称本项目在 2.3 面前「学习引导是明显短板」——**这一判断已不成立**。
上述 2.3 的核心亮点里，本项目**已实现 6 项**，仅剩「反应最慢的键」「单文件打包」等少数差异。

**仍然要规避的坑**：
1. 它为了单文件化把依赖打包进去（892KB）。本项目**天然没有这个问题**（零依赖），
   实现单文件只需内联 CSS/JS，产出会小得多。
2. 它需要 Node ≥ 22.18 且依赖原生 TS 类型剥离，Windows PowerShell 下还要处理执行策略。
   本项目用 `.bat` + 手写 Shell Link 规避了同类问题。

### 2.4 wzukhh/ShuangPin_Study — 纯 HTML/CSS/JS

**简介**：纯 `html + css + js`，主打「装进 U 盘就能用，不需要安装任何开发环境」。

| 设计 | 内容 | 本项目是否适用 | 优先级 |
|---|---|---|---|
| 多方案内置 | 小鹤 / 自然码 / 微软 / 搜狗 / 智能ABC | ✅ 适用 | P0 |
| 明暗主题切换 | 响应式 + 深色模式 | ✅ 适用，成本低 | P2 |
| 虚拟键盘点击输入 | 鼠标点虚拟键盘输入 | ⚠️ 优先级低（物理键盘才是练习目标） | P3 |
| 可直接双击 index.html | 不使用 ES Module | ❌ **不建议效仿** | — |
| 内置 pinyin-pro | 第三方拼音库 | ❌ 与「零依赖」冲突 | — |

**最值得学的一点**：它的**定位表述极清晰**——「装进 U 盘就能用」。
本项目虽然也是零依赖，但受 ES Module 所限**必须起 HTTP 服务**，实际没法双击即用。
这一点上它确实比本项目做得好，而 2.3 的「单文件打包」是解决同一问题的另一条路。

**要规避的坑**：
1. 它为了能双击打开**放弃了 ES Module**，代价是逻辑全挤进全局作用域。
   本项目为了架构清晰选了 ES Module + 起服务，**这个取舍是对的**；
   正确做法是**构建期把 ES Module 内联成单文件**，源码保持模块化，分发产物是单文件。
2. 它的「待办事项」里列了「支持浏览练习历史记录」，说明**历史复盘是缺失的**——
   本项目已有完整的历史曲线与易错表，这块是领先的。
3. `script.js` 承载全部逻辑——**本项目 `main.js` 已 2295 行，再堆功能会失控**，应考虑拆分。

## 四、最值得优先做的 3 项（本版重排）

> 初版的 Top3 已完成，这里给出**当前**真正剩下的三项。

### 🥇 第一优先：结算面板增加「反应最慢的键」

**为什么是第一**：这是 2.3 那套「三维度结算」里**本项目唯一还没做**的一维，
也是三家竞品中「诊断闭环」的最后一块拼图。

本项目已有「最常按错的键」（热力图）与「最容易错的字」（易错表），
但**「按对了但按得慢」反映的是「还在犹豫、没形成肌肉记忆」**——
和「按错」是完全不同的信号，且**更早于错误出现**。补上它，诊断维度就齐了。

**落地要点**：
- 引擎已有 `elapsedSec` 全局计时，但**尚未按「键」维度记录耗时**，
  需要在推进逻辑里把「该键从出现到按下的间隔」累计到 `stats.keyTimings`（键 → 样本数组）
- 结算面板按**中位数**（而非均值，抗异常值）排序，取最慢的前 3–5 个键
- 与热力图共用同一张 SVG，用**另一种视觉编码**区分（例如慢=蓝色描边、错=红色填充），
  避免两个指标在同一张图上互相干扰
- 注意排除「暂停期间」与「首个键」的样本（首个键含反应启动时间，天然偏大）

**风险**：样本少时中位数不稳，需要设置最小样本量门槛（如 ≥5 次）才展示。

---

### 🥈 第二优先：`KeyboardEvent.code` 物理键位判定

**为什么是第二**：**成本极低、收益明确**，属于「一行改动级别」的高性价比项。

当前用 `e.key` 判键，含义是「**字符**」。这在切换了键盘布局（Dvorak、Colemak）或
某些输入法/系统设置下会错位——用户按的是物理上的那个键，但 `e.key` 给出别的字符。
用 `e.code`（如 `KeyV`）判定的是**物理位置**，才是「练键位」这件事真正该对齐的语义。

**落地要点**：
- 在按键归一化处（`normalizeKey` 附近）把 `KeyX` → `x`
- 需要处理 `KeyA`–`KeyZ` 之外的键（分号等）将来可能用于别的方案，先只映射字母区
- 保留 `e.key` 作为**回退**（合成事件、测试环境可能没有 `code`）
- 测试里补 `code` 缺失时的回退断言，避免回归

**风险**：极小。唯一要注意的是别把非字母键误映射进来。

---

### 🥉 第三优先：单文件打包脚本

**为什么是第三**：它解决的是本项目的**唯一分发体验短板**——
「必须起 HTTP 服务才能用」，而这恰恰是 2.4（可双击）比本项目强的地方。

关键是**不要用砍掉模块化的方式**去换双击（那是 2.4 的错），而是像 2.3 那样
**在构建期把 ES Module 内联进单个 HTML**：源码保持模块清晰，分发产物是单文件。

**落地要点**：
- 写一个 `tools/bundle.mjs`：读 `index.html`，把 `<script type="module">` 的模块图
  按依赖顺序内联成一段 `<script>`，把 `<link rel=stylesheet>` 内联成 `<style>`
- ES Module 内联需要处理 `import`/`export` 的改写（去掉 `export`、按拓扑序拼接、
  统一到一个作用域），或改用 `<script type="module">` 内联（现代浏览器支持内联模块脚本，
  但仍受 `file://` 的 CORS 限制 —— **这一点必须先实测**，必要时退化为 IIFE 打包）
- 产物路径不进仓库（或进 `dist/` 并 gitignore），由脚本按需生成
- **不引入打包器**，保持零依赖：用正则/简单的模块图遍历即可（本项目模块数少、无循环依赖）

**风险**：内联模块脚本在 `file://` 下**可能仍被 CORS 拦截**（这是浏览器行为，不是打包问题）。
因此这个任务的第一步应该是**先做可行性验证**：手工内联一个最小模块脚本，
用 `file://` 打开确认能否运行。**验证通过再投入开发**，否则换 IIFE 方案。

## 五、需要规避的坑

### 坑 1：为了「双击即用」而放弃 ES Module ⚠️ 最危险

`wzukhh/ShuangPin_Study` 能双击打开，是因为它**没用 ES Module**，代价是逻辑全挤进全局作用域。
本项目已经吃过 `file://` 不能加载模块的痛，**但解决方案不是砍掉模块化**。

**正确做法**：源码保持 ES Module，写一个构建期脚本把 CSS/JS 内联进单个 HTML。
产出是单文件（可双击、可进 U 盘），源码依然模块清晰。**两头都要，不要二选一。**

### 坑 2：开放自定义双拼方案却不校验合法性

`纸砚` 明确声明「一对多的双拼映射关系**未做兼容**」。
一旦支持多方案（尤其微软双拼的 `ing` 用分号键、零声母用 `O` 前缀），
「双拼码 → 拼音」就可能一对多，导致判定歧义。

**正确做法**：方案配置加载时**先做合法性校验**——拒绝一对多映射，
或明确约定冲突时的优先级规则，并给用户可读的报错。**校验必须在加载期，不能留到判定期。**

### 坑 3：改提示相关代码时不动统计口径

本项目已有「独立正确率 vs 依赖提示」的区分。**任何触碰提示逻辑的改动，
都必须保证这个口径不被破坏**——否则「等提示再按」就能刷满正确率，指标直接作废。
`integration.mjs`【10b】有断言守着这一点，**不要为了让测试变绿而放宽它**。

### 坑 4：`main.js` 继续膨胀

已 2295 行（比初版报告时又长了 446 行）。再往里堆功能会失控。
**建议在做新功能之前先拆**：至少按视图拆成 `views/practice.js`、`views/stats.js`、
`views/settings.js`、`views/review.js`、`views/keymap.js`。

### 坑 5：引入 TS + Vitest + ESLint

这是「看起来更专业」的陷阱。本项目现有测试已覆盖
方案正确性 / 引擎逻辑 / 全应用集成三个层面，并且有全量遍历断言——
**测试质量并不低，只是工具朴素**。引入完整工具链会带来：
- 必须 `npm install`（运行时）
- 改变「改完刷新即生效」的开发体验
- 违背「零依赖零构建」的核心定位

**CI 的需求已用 GitHub Actions 单独满足**（不依赖 TS/Vitest/ESLint），这一条不必再动。

### 坑 6：题库「越大越好」的误区

`2.3` 有 12000 词，本项目 299 词。但**练习效果不取决于绝对数量，而取决于覆盖度与梯度**。
本项目已有全部音节 100% 为 2 键的全量校验，覆盖度是完整的。
盲目扩到上万词，反而会让「易错复习」的样本被稀释。
**优先做的是「按字频加权」和「提高梯度合理性」，而不是堆量。**

## 六、总结

| 维度 | 本项目现状 | 与同类对比 |
|---|---|---|
| 架构分层 | ✅ 干净（core/ui/data 分离，core 不碰 DOM） | **优于** 2.4，与 2.2 相当 |
| 方案正确性 | ✅ 全量音节校验 + 候选数组设计严谨 | **优于** 多数（多数用单一答案） |
| 测试 | ✅ 三套套件 + 全量遍历 + 确定性回归 + 锁文件 + CI | **优于** 2.1/2.3/2.4，与 2.2 相当 |
| 零依赖 | ✅ 运行时完全没有依赖树 | **优于** 2.1/2.2/2.3，与 2.4 相当 |
| **学习引导** | ✅ **卡住提示 + 分级求助 + 独立正确率口径** | **与 2.3 持平**（初版误判为明显弱） |
| **薄弱点诊断** | ✅ 易错字词表 + 键位热力图 + 范围切换 | **与 2.3 持平**，仅差「反应最慢的键」 |
| 练习模式粒度 | ✅ 8 种，含声母/韵母专项与无提示测验 | **优于** 2.2/2.3 |
| 分发体验 | ⚠️ 需起服务（有 .bat 补偿），无单文件 | 弱于 2.3（单文件）、2.4（双击） |
| 方案可扩展性 | ❌ 硬编码小鹤，加方案要改核心 | **明显弱于** 2.1/2.2/2.4 |
| 代码组织 | ⚠️ `main.js` 2295 行偏大 | 弱于 2.2（有框架分层） |

**一句话结论**：
本项目的**工程底子（分层、测试、方案严谨度、依赖可复现性）在同类中属于上游**，
**「学习引导」与「薄弱点诊断」两块短板已经补齐**（这是初版报告最大的误判）。
当前真正的差距收敛到两点：

1. **分发体验**——需要起服务，没有单文件产物（→ 优先项 🥉）；
2. **方案可扩展性**——硬编码小鹤，加方案要改核心（→ 优先级 P1，但要连同合法性校验一起做）。

在此之前，建议先补上成本最低、收益明确的**「反应最慢的键」**与**物理键位判定**，
把诊断闭环彻底做完整，再动「分发」与「多方案」这两块较大的工程。
