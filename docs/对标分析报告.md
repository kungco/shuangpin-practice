## 一、本项目定位画像

### 1.1 核心定位

**一个零依赖、零构建、可离线运行的小鹤双拼练习网页应用。**

从代码结构反推出的三条设计主线（这三条决定了它与同类项目的根本差异）：

| 主线 | 具体表现 | 代价 |
|---|---|---|
| **零依赖** | 全仓库无 `package.json`、无构建工具、无运行时第三方库。`src/` 下全部是原生 ES Module | 无法用 TS/框架/组件库，`main.js` 已 1849 行 |
| **零构建** | `index.html` 直接 `<script type="module" src="src/main.js">`，改完刷新即生效 | 必须起 HTTP 服务（`file://` 下 ES Module 被 CORS 拦截） |
| **离线优先** | 题库、方案、图表全部内置。`ui/chart.js` 是手写 Canvas 图表（342 行），**刻意不引图表库** | 图表能力受限，只有折线/柱状两种 |

> **关键取舍**：为了「零依赖」，本项目付出了 `file://` 不能直接双击的代价（ES Module 的硬限制），只能靠 `启动双拼练习.bat` 起本地服务来补偿。这是一个**用一点使用摩擦换取架构纯净**的选择。

### 1.2 技术栈

```
语言      原生 JavaScript（ES2020+，ES Module）
样式      原生 CSS（单文件 843+ 行，CSS 变量着色）
图形      SVG 手绘键盘（ui/keymap.js）+ Canvas 手绘图表（ui/chart.js）
存储      localStorage（带内存降级 + 配额恢复）
测试      自研零依赖测试脚本（.mjs）+ linkedom 驱动集成测试
分发      Windows .bat 一键启动（含手写 Shell Link 生成桌面快捷方式）
```

**没有的东西**（要明确）：无 TS、无框架、无打包器、无 npm 依赖树、无 CI 配置、无 Lint 配置。

### 1.3 架构分层

```
┌─────────────────────────────────────────────┐
│  main.js (1849行)  应用装配 / 视图渲染 / 事件 │  ← 唯一的大型文件
├─────────────────────────────────────────────┤
│  ui/     keymap.js(SVG键盘)  chart.js(Canvas)│
├─────────────────────────────────────────────┤
│  core/   engine.js(状态机)  questions.js(出题)│
│          scheme.js(方案)    stats.js(统计)   │
│          storage.js(存储)   tokenizer.js(分词)│
├─────────────────────────────────────────────┤
│  data/   pinyin.js(945字/299词/45短文)       │
└─────────────────────────────────────────────┘
```

**分层是干净的**：`core/` 完全不碰 DOM，`ui/` 只做渲染、不含业务逻辑，`data/` 是纯数据。
`scheme.js` 把方案抽象成「拆解候选数组」而不是单一答案，这一点设计得比多数同类项目更严谨
（因为 `xian` 可以是 `x+ian` 也可以是 `xi+an`，单一答案会误判）。

### 1.4 功能清单

| 模块 | 能力 |
|---|---|
| 练习模式 | 5 级：键位熟悉 / 音节拆分 / 单字(6档递进) / 词组 / 短文跟打 |
| 实时反馈 | 逐键校验、错误时给正确键+拆分方式、实时速度/正确率/用时 |
| 键位图 | 交互式 SVG，实时高亮当前按键的声母与韵母 |
| 统计 | 每日数据、速度/正确率/字数三种曲线（日/周/月）、易错字词表 |
| 复习 | 易错项按「错误次数 × 时间衰减 × 掌握惩罚」加权，一键生成复习题 |
| 体验 | 自定义时长/题量、暂停续练、现场恢复、JSON 导出导入 |
| 容错 | 存储降级、配额恢复、脏数据过滤、非 2 键音节全量拦截 |

### 1.5 工程化亮点（已做得比同类好的部分）

- **测试组织**：三套独立套件（verify 方案正确性 / engine 引擎逻辑 / integration 全应用），
  全部零依赖（除 linkedom）。`verify.mjs` 里有**全量遍历断言**——4307 个音节逐个校验必须 2 键。
- **文档**：README 记录了「容易踩的坑」；`_test/README.md` 说明了测试环境的两处降级垫片
  （明确区分「测试框架缺陷」与「应用缺陷」），这个意识很少见。
- **数据校验流水线**：`_test/gen_expand.mjs` 用真实引擎校验候选内容，全过才写盘。
- **构建期脚本与运行时严格分离**：`_test/` 可整个删除，不影响应用。

|---|---|---|---|
| **多方案支持** | 内置 20+ 方案：自然码/搜狗/微软/小鹤/智能ABC/拼音加加/紫光/国标/小浪/大牛/蓝天/键道/星空/开源小鹳/小月… | ✅ **高度适用** | **P0** |
| **方案配置与代码分离** | 新增方案 = 在 `src/scheme/` 加一份拼音映射配置 + 在 `scheme-list.js` 注册，**不改核心逻辑** | ✅ **高度适用** | **P0** |
| **键位图自动渲染** | `npm run build:svg` 从 `keyboard/scheme/*.js` 配置渲染出 SVG/PNG | ⚠️ 部分适用（本项目是运行时渲染，更灵活，不需要这一步） | P3 |

| **多平台适配** | Web + 微信小程序共用核心逻辑 | ⚠️ 小程序需重构 DOM 层，成本高 | P3 |

**最值得学的一点**：它的「新增一个双拼方案」是一条**文档化的 8 步流程**，任何人都能照着加。
本项目目前把方案硬编码在 `scheme.js` 的 `XIAOHE_LAYOUT` 常量里，加第二套方案要改核心代码。

**要规避的坑**：README 明确写着「Web 版键位图如果不能正常显示（如内容排版错乱或重叠），
请尝试更新最新版 Chrome」——说明它的键位图渲染对浏览器有依赖，且**曾出现过文字重叠问题**。
本项目正好踩过同一个坑（H 键 `ang` 与提示文字重叠），并且**用几何断言测试守住了**，
这一点本项目做得更好，不要退化成「靠浏览器兼容性蒙」。

### 2.2 Yidadaa/shuangpin —「纸砚」（自称「最好用」）

**简介**：Vite + TypeScript + Vitest 构建，支持声母/韵母/长句模式、自定义方案、进度统计、深色模式、成就系统。

**值得借鉴的设计**

| 设计 | 内容 | 本项目是否适用 | 优先级 |
|---|---|---|---|
| **练习模式按「知识点」而非「文本长度」划分** | 随机 / **声母模式** / **韵母模式** / 长句模式 | ✅ **高度适用** | **P0** |
| **自定义方案配置格式** | `keyMap: { "q/iu/q": ... }`，一行同时声明 键位/韵母/声母；`zeroMap: { "aa/a" }` 声明零声母 | ✅ **高度适用** | **P0** |
| **本地自定义方案** | 用户可在设置里现场新增方案，不必改源码 | ✅ 适用 | P1 |
| **Vitest 单测 + Husky + ESLint + GitHub Actions** | 完整工程化链路 | ⚠️ 与「零依赖」定位冲突 | P2 |
| **多音字处理** | 多音字候选列表过长时截断显示，但**仍可正常判定** | ✅ 适用（本项目短文已覆盖，但多音字未专门处理） | P2 |
| **成就系统** | 持续激励（README 标 WIP） | ✅ 适用，成本低 | P2 |

**最值得学的一点**：「声母模式 / 韵母模式」这个切分方式比本项目的「音节拆分」更对症。
理由：新手做完整音节练习时，按错了**分不清是声母没记住还是韵母没记住**。
把两者拆开单独练，能精确定位薄弱环节。本项目的 L2「音节拆分」是整体的，粒度不够。

**要规避的坑**：README 的 FAQ 里有一条很关键——
> 「为什么自定义双拼模式下，某些拼音无法识别？请检查自定义方案是否出现了一对多的双拼映射关系…
> 这样会导致重码率上升，所以**并未对此类方案做兼容**。」

也就是说：**开放自定义方案后，必须定义并校验「方案合法性」**，否则会遇到
「双拼码 → 拼音」一对多导致判定歧义。本项目如果要支持多方案，必须一并设计好这层校验
（微软双拼的 `ing` 用分号键、零声母用 `O` 前缀，这些差异都会撞上这个问题）。

## 四、最值得优先借鉴的 2–3 项

### 🥇 第一优先：卡住自动提示

**为什么是第一**：它填补的是**本项目最大的体验缺口**。

当前逻辑是「按错 → 给反馈」。但真实学习场景里，新手更多是**卡住想不起来**，
此时应用毫无帮助，用户只能干等或乱按。这个功能把「求助」变成了一等公民。

**落地要点**：
- 计时器：某个键位停留超过 3 秒 → 在键位图上闪烁该键（复用现有 `highlightForSplit`）
- 按任意键后重置计时
- **统计口径必须调整**：新增「依赖提示」计数，`提示过的题不计入独立正确率`
  （否则用户会用提示刷高分，正确率就失去意义）
- 分级：默认只闪键位不给答案；`Tab` 显示答案；可在设置里开「6 秒自动显示答案」
- 暂停/准备阶段**不能**触发提示（2.3 明确提到了这个坑）

**风险**：如果不改统计口径，正确率指标会被污染。这是必改项，不是可选项。

---

### 🥈 第二优先：错误热力图

**为什么是第二**：它是「练习 → 洞察 → 针对性改进」闭环的最后一环，而这一环本项目目前是弱的。

本项目已有易错字词表，但那是**文字列表**。热力图把同样的数据**直接着色回键盘**，
用户一眼就能看出「我右边这一片键都不熟」。认知效率完全不同。

**落地要点**：
- 本轮热力图：实时随按键更新
- 历史累计热力图：需要 `storage.js` 增加「按键错误计数」的持久化（当前只存了错误字词，没存键位维度）
- 支持范围切换：全部历史 / 最近 30 次 / 最近 10 次
- 复用 `keymap.js` 的 SVG，只改 fill 颜色，成本很低

**风险**：单次练习数据噪声大（按错 2 次可能只是手滑），所以**累计视图比单轮视图更有价值**，
两个都要有，但默认展示累计。

---

### 🥉 第三优先：声母/韵母拆分练习

**为什么是第三**：它解决的是**「诊断粒度」问题**。

本项目 L2「音节拆分」是整体的——用户按错 `zhang` 的 `V`，
反馈只会说「zhang 应该是 VH」，但**分不清是声母 zh 没记住，还是韵母 ang 记混了**。
把两者拆成独立练习，就能精确定位。

**落地要点**：
- 复用 `questions.js` 的出题器，新增两种模式
- 声母模式：给韵母固定的音节，只练声母键
- 韵母模式：给声母固定的音节，只练韵母键
- 与 2.3 的「键位记忆训练」（韵母→键 / 声母→键 / 音节→声母键 / 音节→韵母键）本质相同，
  可以一次做四个子模式

**风险**：模式变多后，**设置页的认知负担会上升**。需要合理分组，
不能简单地把 5 种模式堆成 9 种。

## 五、需要规避的坑

### 坑 1：为了「双击即用」而放弃 ES Module ⚠️ 最危险

`wzukhh/ShuangPin_Study` 能双击打开，是因为它**没用 ES Module**，代价是逻辑全挤进全局作用域。
本项目已经吃过 `file://` 不能加载模块的痛，**但解决方案不是砍掉模块化**。

**正确做法**：源码保持 ES Module，写一个构建期脚本把 CSS/JS 内联进单个 HTML。
产出是单文件（可双击、可进 U 盘），源码依然模块清晰。**两头都要，不要二选一。**

### 坑 2：开放自定义双拼方案却不校验合法性

`纸砚` 明确声明「一对多的双拼映射关系**未做兼容**」。
一旦支持多方案（尤其微软双拼的 `ing` 用分号键、零声母用 `O` 前缀），
「双拼码 → 拼音」就可能一对多，导致判定歧义。

**正确做法**：方案配置加载时**先做合法性校验**——拒绝一对多映射，
或明确约定冲突时的优先级规则，并给用户可读的报错。**校验必须在加载期，不能留到判定期。**

### 坑 3：不改变统计口径就上「提示」功能

见上。不引入「独立正确率 vs 依赖提示」的区分，正确率就废了。

### 坑 4：`main.js` 继续膨胀

已 1849 行。上面任何一项功能加进去都会让它更臃肿。
**建议在做功能之前先拆**：至少按视图拆成 `views/practice.js`、`views/stats.js`、
`views/settings.js`、`views/review.js`、`views/keymap.js`。

### 坑 5：引入 TS + Vitest + ESLint + CI

这是「看起来更专业」的陷阱。本项目现有测试已覆盖
方案正确性 / 引擎逻辑 / 全应用集成三个层面，并且有全量遍历断言——
**测试质量并不低，只是工具朴素**。引入完整工具链会带来：
- 必须 `npm install`
- 改变「改完刷新即生效」的开发体验
- 违背「零依赖零构建」的核心定位

**除非项目要开始多人协作，否则不建议。** 现有 `.mjs` 测试脚本可以继续加强。

### 坑 6：题库「越大越好」的误区

`2.3` 有 12000 词，本项目 299 词。但**练习效果不取决于绝对数量，而取决于覆盖度与梯度**。
本项目已有 4307 个音节全量校验 100% 为 2 键，覆盖度是完整的。
盲目扩到上万词，反而会让「易错复习」的样本被稀释。
**优先做的是「按字频加权」和「提高梯度合理性」，而不是堆量。**

## 六、总结

| 维度 | 本项目现状 | 与同类对比 |
|---|---|---|
| 架构分层 | ✅ 干净（core/ui/data 分离，core 不碰 DOM） | **优于** 2.4，与 2.2 相当 |
| 方案正确性 | ✅ 4307 音节全量校验，候选数组设计严谨 | **优于** 多数（多数用单一答案） |
| 测试 | ✅ 三套独立套件 + 全量遍历断言 | **优于** 2.1/2.3/2.4，弱于 2.2 的工具链 |
| 零依赖 | ✅ 完全没有依赖树 | **优于** 2.1/2.2/2.3，与 2.4 相当 |
| 分发体验 | ⚠️ 需起服务（有 .bat 补偿） | 弱于 2.3（单文件）、2.4（双击） |
| **学习引导** | ❌ **只有「按错才反馈」，没有「卡住求助」** | **明显弱于 2.3** |
| **薄弱点诊断** | ⚠️ 有易错字词表，无键位热力图 | **弱于 2.3** |
| 方案可扩展性 | ❌ 硬编码小鹤，加方案要改核心 | **明显弱于 2.1/2.2/2.4** |
| 练习模式粒度 | ⚠️ 5 级，声韵未拆开 | 弱于 2.2/2.3 |

**一句话结论**：
本项目的**工程底子（分层、测试、方案严谨度）在同类中属于上游**，
真正的差距在**「学习引导」这一层**——同类最好的项目已经做到「卡住有人扶、错了有人指路」，
而本项目还停留在「错了给个提示」。
**下一步应该把预算全部投在「提示与诊断」上（第 1、2、3 优先项），而不是堆功能或换技术栈。**
